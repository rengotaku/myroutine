# ADR 0005: 定常のやることを第 3 のチャネル (add_todo) に分ける

## 背景

ADR 0002 でサマリを「要対応」と「情報」に分けた。要対応は劣化検知の枠で、同じ id が
続けて出ると連続日数が付き、閾値を超えると赤く強調される。

運用していると、この 2 枠のどちらにも収まらないものが出てきた。**毎日必ずそこにある
定常のやること**である。実例は「その日の進捗報告をまだ作っていない」という掲示で、
掲示する側の routine と、実際にそれを回す作業とを並行して回す運用だったため、routine が
先に走る以上、成果物は毎回まだ存在しない。

これを要対応に載せた結果、劣化していないのに連続日数だけが 9 日まで伸びた。連続日数は
「放置されている」ことを示すための表示なので、放置されていないものに付くと表示自体が
信用を失う。要対応ボックスに毎日居座る 1 件があると、その隣に出た本物の劣化も同じ濃度で
読み飛ばされる。

## 決定

第 3 のチャネル `add_todo <id> "<きょう回すもの>"` を追加し、サマリに「📋 きょう回すもの」
として要対応と情報の間に出す。

**このチャネルは `history.tsv` に記録しない。** 連続日数・NEW・解消はいずれも履歴の
比較から導かれるので、記録しないことがそのまま「劣化検知の対象外」になる。判定を
分岐させるフラグを足すのではなく、そもそも履歴に載せない形にした。

枠の意味は 1 枠 1 つに保つ:

| 枠 | 入口 | 意味 | 履歴 |
|---|---|---|---|
| ⚠ 要対応 | `add_action` | 本来は無いはずのものが出ている＝劣化 | 記録する |
| 📋 きょう回すもの | `add_todo` | 毎日そこにある定常のやること | 記録しない |
| ℹ 情報 | `add_info` | 自動で済ませた事後報告 | 記録しない |

## 検討して捨てた案

### 情報枠 (`add_info`) に相乗りさせる

追加実装が要らない。捨てた理由は、情報枠の定義が ADR 0002 で「自動実行済みの事後報告」と
定まっているため。やることを混ぜると 1 枠が 2 つの意味を持ち、読み手は行ごとに「これは
済んだ話か、これからやる話か」を判別しなければならなくなる。枠を分けた意味が消える。

### 要対応に載せたまま、連続日数の対象外にするフラグを足す

`add_action -q` のような抑制フラグで済ませる案。捨てた理由は、表示の枠は同じままなので
「要対応 3 件」の件数に定常のものが混ざり続けること。件数はボックスを読むかどうかの
最初の判断材料なので、ここが水増しされるとフラグでは救えない。

### ステップ本文にだけ書く

`info` で本文に出し、サマリには載せない案。捨てた理由は ADR 0002 と同じで、ステップ本文は
流し読みで見落とされる。サマリに集約することが routine runner の存在理由である。

## 前提

**変えてよい**: 見出しの文言・記号（📋 / □）、3 枠の並び順。

**壊すと危ない**: `add_todo` を履歴に記録しないこと。記録すると `_mr_analyze_history` が
定常の id を毎日の連続として数え始め、本 ADR が解こうとした問題がそのまま戻る。また
劣化（本来は無いはずのもの）を `add_todo` に載せてはいけない。履歴に残らないため、
放置されていることが誰にも見えなくなる。
