# ADR 0002: 要対応と情報を別チャネルに分け、要対応に安定 id を持たせる

## 背景

routine runner の中心的な出力は「人間がこれから何をすべきか」の一覧である。ここに
自動処理済みの事後報告（「古いファイルを N 件消しました」）を混ぜると、対応が必要な
項目が埋もれる。かといってステップ本文にだけ出すと、流し読みで見落とす。

さらに、運用中に 2 回、**サマリが機能しなくなっていることに人間が長期間気づかない**
という事故が起きた。

1. 集計方法の誤りで、棚卸しを済ませても翌日また同じ要対応が掲示され続けた
2. 判定条件が厳しすぎ、特定の 1 件が毎日掲示され続けた

どちらも「毎日同じものが出ている」ことを検知する仕組みが無かったのが原因である。

## 決定

### チャネルを 3 つに分ける

| 枠 | 用途 |
|---|---|
| ステップ本文 | 逐次の進捗。流し読みされる前提 |
| 要対応（`add_action`） | 人間がこれから何をすべきか |
| 情報（`add_info`） | 自動処理済みの事後報告。対応不要 |

### 要対応に安定 id を持たせる

`add_action <id> "<本文>"` とし、本体がステップのファイル名から導いた slug を前置して
`<slug>.<id>` に正規化する。

- 本文には件数などの可変値が入るため、本文を追跡キーにできない
  （「未分類 3 件」と「未分類 4 件」が別物になる）
- slug はファイル名の `NN-` を除いた部分なので、**順序を変えるリネームでは変わらない**
- 実行ごとに id 集合を履歴へ追記し、連続掲示日数・NEW・解消を算出する

### 履歴を汚さない条件

- `--dry-run` は実際の状態ではないので記録しない
- 部分実行と、途中で中断した実行は要対応の集合が欠けるため記録しない。記録すると
  「今日は出なかった」と誤って解消扱いになり、連続日数が壊れる。部分実行では
  解消・NEW の判定自体も行わない
- 全ステップを回した実行でも、**成功しなかったステップは「見ていない」**（skip も
  失敗もタイムアウトも、要対応の有無を確認しきれていない）。履歴に「その実行で
  成功したステップの slug」を併記し、解消判定と連続日数の対象をそこに限定する。
  これが無いと、前提コマンドが一時的に無いだけ・判定前に落ちただけで前回の
  要対応が解消扱いになる
- **NEW / 解消は「前回の実行」との比較**なので、当日の先行実行も比較対象に含める
  （連続「日数」の計算からは当日を外す）

## 捨てた案

- **`add_action` に相乗りさせて情報も同じ枠に出す**: 実装は簡単だが、対応必須項目が
  埋もれるという当初の問題がそのまま残る
- **本文のハッシュを追跡キーにする**: id を書かせずに済むが、件数が変わるたびに
  別物になるため滞留を検知できない。この機能の目的そのものを達成できない
- **id を必須にせず省略可にする**: 省略されたものだけ追跡から漏れ、「一部だけ
  滞留が見える」中途半端な状態になる。書き忘れが機能の穴になるので必須にした

## 変えてよい前提 / 壊すと危ない前提

- **変えてよい**: 強調する連続日数のしきい値、表示の文言、履歴ファイルの保持期間
- **壊すと危ない**:
  - id に可変値（件数・日付・パス）を含めないこと。含めると滞留を検知できなくなり、
    この機能が存在する意味がなくなる
  - dry-run と部分実行を履歴に記録しないこと。記録すると解消判定が誤り、
    連続日数が毎回リセットされる
  - slug をファイル名の `NN-` を除いた部分から導くこと。ここを番号込みにすると、
    順序変更のリネームで全 id が変わって履歴が切れる
