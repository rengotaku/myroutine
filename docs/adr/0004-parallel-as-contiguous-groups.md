## 背景

全実行の所要時間はほぼ待ちで埋まっていた。2026-08-21 の実測では network 41.4s /
aws-sso 26.1s / dotfiles 21.6s / worktree 19.9s に対し、残り 5 ステップの合計が 25s 未満。
上位のステップはいずれもネットワーク待ちが支配的で、CPU も互いのファイルも競合しない。

一方で FW には並列化と相容れない仕組みがある。破壊的ステップのゲートは `confirm` で stdin を
読み、`step_abort_on_fail` は「後続を止めるか」を尋ね、要対応の集約と結果の記録は親の配列に
書く。素朴に全部を同時に走らせると、プロンプトが混線し、記録が失われる。

## 決定

`step_parallel=true` をオプトインで追加し、**実行順で連続する parallel ステップを 1 グループ
として同時実行する**。グループは逐次ステップを跨がない。

- ゲート（前提・実行間隔・破壊的）と結果の記録は親で行う。背景に出すのは実行だけ
- 出力はステップ単位にファイルへ溜め、グループ完了後に**ステップ番号順**で流す
- 同時実行数は `MYROUTINE_PARALLEL_MAX`（既定 4）で上限を設ける
- `step_parallel` と `step_destructive` / `step_abort_on_fail` の併用は discover の時点で
  エラーにする
- `confirm` は並列コンテキストでは tty を読まず中止側に倒す

## 理由

**グループ化の単位を「実行順の連続範囲」にした。** 並び順はファイル名で決まるので、どこで
区切るかは番号付けだけで制御できる。本体に新しい概念（依存の宣言）を持ち込まずに、既にある
順序の仕組みをそのまま使える。

**出力を番号順に flush する。** 並列化で得たいのは所要時間の短縮だけで、見え方が変わることは
損失でしかない。端末・日次ログ・サマリの並びが実行のたびに揺れると、日次ログの差分が読めなく
なる。溜めた出力を番号順に流せば、逐次との差は所要時間にしか出ない。

**併用の禁止を実行時ではなく宣言時に落とす。** 「走らせてみるまで分からない」形にすると、
破壊的ステップを並列にした設定ミスが、確認の混線という分かりにくい症状で現れる。discover で
落とせば `myroutine ls` の時点で気づける。

**`confirm` を中止側に倒すのは既にある規律の延長。** tty が取れない環境（パイプ実行・CI・
スケジューラ経由）で中止側へ倒す扱いが既にあり、並列コンテキストも「誰の問いか分からない
答えを受け取りうる」という点で同じ。承認を得たことにしてしまうより安全側に倒す。

## 捨てた案

**依存グラフを宣言させる（`step_after=(network)`）。** 表現力は上がるが、本体に依存解決と
循環検出が要る。今欲しいのは「隣接する数ステップを同時に走らせる」だけで、そのために本体が
知る概念を増やす取引が悪い。順序の制御手段としてファイル名順が既にあり、二重になる。

**既定で全ステップを並列にし、逐次にしたいものを宣言させる。** 既存のステップが全て「逐次で
あること」を前提に書かれているため、既定を変えると読み取りきれない壊れ方をする。オプトインなら
宣言したステップだけが新しい規約に入る。

**空いた枠を最速で埋めるスケジューラ。** 先頭の pid から順に待つ形（head-of-line）を採った。
グループ全体が終わるまで回すので総所要時間は変わらず、pid の追跡が単純に保てる。グループの
大きさが数ステップである限り、精緻なスケジューリングで得るものが無い。

## 変えてよい前提 / 壊すと危ない前提

- 変えてよい: `MYROUTINE_PARALLEL_MAX` の既定値、待ち方（head-of-line）
- 壊すと危ない: **記録（`_mr_record` / `_mr_actions`）を親以外で行うこと。** サブシェルから
  親の配列は変更できないため、背景に出した処理が要対応を書くと黙って失われる
- 壊すと危ない: **出力を番号順に flush する保証。** 完了順に流すと日次ログの差分が読めなくなる
- 壊すと危ない: **報告チャネル・タイムアウトマーカーがステップ単位であること。** 共有すると
  並列時に互いの報告を上書きする
