# ADR 0001: routine runner 本体の実装言語に zsh を選ぶ

## 背景

本体は日次ルーティンを回す単一の zsh スクリプトとして育ってきた。FW 部分を切り出すにあたり、
実装言語を選び直す機会があった。

売りにしたい 3 点（安全にコマンドを実行する / 利便 / 可視化）のうち、安全と可視化の要件は
ちょうど zsh の弱いところに集中している。

- 多重起動ロックの定番である `flock` は macOS に存在しない
- ステップ単位のタイムアウトに使える `timeout` コマンドも macOS の標準にはない
- JSON 出力・履歴の差分計算は、文字列組み立てで書くことになる

## 決定

**zsh のまま実装する。** ステップも shell のまま置く。

代償は次のように埋める。

- **ロック**: `mkdir` のアトミック性で排他する。ロックディレクトリに pid を書き、
  取得できなかったときは pid の生存を確認して stale なら回収する。判断がつかない場合は
  必ず中止側へ倒す
- **タイムアウト**: 監視プロセスを併走させ、時間切れならマーカーを置いてから対象を落とす。
  プロセス木を数え上げてから一括で kill する（順に辿って kill すると取りこぼす。
  取りこぼした子孫はログ用パイプを掴んだまま残り、実行全体が終われなくなる）
- **JSON**: 手書きのエスケープ関数を用意し、テストで妥当性を検証する

## 捨てた案

**Go で書き直す（単一バイナリ配布）。** ロック・タイムアウト・JSON・テストのいずれも
標準ライブラリで素直に書け、周辺の私製ツールも Go に寄っている。実際こちらが技術的には
有利だった。

採らなかった理由:

- ステップは shell で書く前提であり、本体を Go にすると「Go が親、shell が子」の境界を
  跨いでプリミティブ（`capture` / `run` / `confirm`）を提供する層が別途必要になる。
  この層は本体そのものより複雑になりうる
- 既存のステップ資産をそのまま `steps.d/` へ移せる利点が大きい
- 導入に Go ツールチェーンが要らない

## 変えてよい前提 / 壊すと危ない前提

- **変えてよい**: 既定タイムアウト値、ロックの再試行回数、JSON のフィールド追加
- **壊すと危ない**:
  - タイムアウト時の kill は「木を全部数え上げてから一括で落とす」順序。ここを
    「親から順に辿って kill」に戻すと、孫が里子に出て pgrep で辿れなくなり、
    ログ用パイプを掴んだ孤児が残って実行全体がハングする
  - 監視プロセスの出力は握り潰すこと。ログ用パイプを掴んだまま残ると同じくハングする
  - ロックが取得できないときの既定は「中止」。ここを「続行」に倒すと多重起動で
    パッケージ管理と git を同時に触る
