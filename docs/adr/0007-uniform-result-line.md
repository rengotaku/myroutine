# ADR 0007: 結果行の書式を状態によらず 1 つにし、成功の一言を実行のたびに検査する

## 背景

ステップの結果は、状態ごとに出し方がばらばらだった。

- 成功と失敗はレンダラが `✓` / `✗` の結果行として出すが、所要時間の後ろに `rc=1` や
  `終了 08:45` が付き、どこまでが何の情報か読みにくかった
- 前提不足と見送りの skip は、runner が診断メッセージとして `⊘ skip: 前提が足りません（コマンド: x）`
  を自由文で出していた。位置も名前も無く、「前提」が何を指すのか画面からは分からない
- 成功の一言（`emit_summary`）は任意で、25 本中 5 本が出しておらず、出しているものも
  `clean` / `killed 0 / stale 0` のように英語と日本語が混ざっていた

表示を一度揃えても、ステップを足したり直したりするたびに同じブレが戻る。ステップを書く
人に委ねられた部分が、規約として決まっておらず検査もされていなかったためである。

## 決定

1. 結果行は状態によらず `記号 [位置/全件] 名前  一言  所要時間` の 1 つの書式にする
   - 成功: 一言は `emit_summary`。出さなければ `要約なし`
   - 失敗: `失敗（終了コード N）` / `timeout（N 秒）`
   - skip: `skip（<理由>）`。理由は `<コマンド/パス> が無い` / `確認で N` / `dry-run`。
     実行していないので所要時間は出さない
   - 実行間隔による skip だけは途中に出さず、末尾の「今日は対象外」にまとめる（ADR 0003 の skip の扱いは変えない）
2. 終了時刻は出さない。開始行の時刻と所要時間から求まり、新しい情報が無いため
3. 失敗と skip の一言は runner が step イベントの status / rc / note から組み立てる。
   ステップからは書けないので、ステップを足してもブレない
4. ステップに任される成功の一言には規約を置き、runner が成功のたびに検査する。
   違反は要対応に `<slug>.__summary` として積む（終了コードは変えない）
   - 必ず出す / 「完了」「成功」「OK」を含めない / 英単語（3 文字以上、大文字だけの略語は除く）を含めない / 40 カラム以内

## 検討して捨てた案

- **ステップファイルを読み込み時に grep して `emit_summary` の有無を見る**: 条件分岐の奥で
  呼ぶステップや、分岐によって呼ばない経路を見分けられない。実行後に実際に出た一言を
  見る方が判定が正確で、実装も小さい
- **長いステップだけに終了時刻を残す**: 「長さで選り分けない（判定を持たない方が単純）」という
  開始行の決定（#43）と矛盾する
- **違反を失敗扱いにする**: 表示の規約違反でステップの成否を変えると、本来の失敗検知
  （critical・劣化検知）の信用が落ちる。要対応に載せれば劣化検知の連続日数で放置も見える

## 変えてよい前提 / 壊すと危ない前提

- 変えてよい: 一言の上限幅、禁止語の一覧、英単語の判定（文字数・略語の扱い）
- 壊すと危ない: skip の note の形式（`コマンド: x, パス: y` / `declined (destructive)` /
  `dry-run (destructive)` / `cadence: ...`）。レンダラはこれを画面向けの理由に直しており、
  runner 側で形を変えると理由がそのまま生で出る
- `MYROUTINE_SUMMARY_CHECK=0` は一言を出さない仮のステップを使う統合テストのためのもの。
  運用で切ると、ステップを足したときのブレを拾えなくなる
